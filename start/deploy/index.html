部署上线

把本地可用的版本变成可访问、可回退的网站。

S 计划上站路线04 / 08 · 更新于 2026.10.04

本阶段目标：获得稳定可访问的正式网址。

最小路线：先提交代码到 GitHub，再用熟悉的平台发布静态站；可从 Cloudflare Pages 的 Git 集成开始，验证平台地址后再绑定自有域名；有后端的项目按 Vercel 或 Cloudflare 对应运行时文档部署。

完成标准：正式地址的 HTTPS、资源、功能、内页与手机验收通过，并记录可回退版本。

操作步骤

步骤做什么完成判据常见卡点
保存待发布版本确认本地验收通过，提交本次相关文件，记录版本和主要修改内容。能定位本次发布的代码版本，并找回上一版。不要把密钥、缓存或与任务无关的文件一起提交。
选择适合的部署入口静态文件选静态托管；需要构建时按项目实际命令填写；后端、登录、数据库另核平台支持。部署方式符合代码运行要求，构建命令与输出目录有依据。GitHub Pages 只提供静态托管，不能直接运行通用后端。
先验平台地址连接仓库，执行部署，打开平台地址检查首页、资源和直接访问内页。部署记录成功，刷新内页与核心功能均正常。子路径、大小写、构建输出目录出错时先看部署日志，不急着改域名。
绑定域名与 HTTPS按平台说明添加域名及 DNS 记录，等待验证，确定一个正式地址并核对其他地址的跳转。正式网址证书正常，没有混合内容，页面资源完整。不要在证书或解析未完成时反复改配置；记录变更时间便于排查。
完成上线验收换手机或浏览器访问正式地址，再跑验收例子，检查外链、新窗口、404 与页面返回。留下一份地址、版本、验收结果和回退办法。本地通过不等于线上通过；实际用户应拿到正式链接。
